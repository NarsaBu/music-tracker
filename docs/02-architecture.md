# 02 — Архитектура

## 1. Компоненты

```
┌──────────────┐   HTTPS/JSON    ┌─────────────────────────────────────────┐
│  React SPA   │ ──────────────▶ │                Backend (Go)             │
└──────────────┘                 │                                         │
                                 │  HTTP API ─┐                            │
┌──────────────┐   Atom/RSS      │            ├─▶ Use cases ─▶ Ports       │
│  RSS-ридер   │ ──────────────▶ │  Feeds ────┘        ▲                   │
└──────────────┘                 │                     │                   │
                                 │  Scheduler ─────────┘                   │
                                 │  Workers (sync, import, outbox)         │
                                 └───┬──────────────┬──────────────┬───────┘
                                     │              │              │
                              ┌──────▼─────┐ ┌──────▼──────┐ ┌─────▼─────┐
                              │ PostgreSQL │ │ MusicBrainz │ │   SMTP    │
                              └────────────┘ │  (1 RPS)    │ └───────────┘
                                             └─────────────┘
```

Backend — **один бинарь** с подкомандами:

| Команда | Назначение |
|---------|------------|
| `tracker serve` | HTTP API + фиды + планировщик + воркеры (режим по умолчанию, MVP) |
| `tracker migrate up/down` | Миграции БД |
| `tracker sync --artist=<mbid>` | Ручной прогон синхронизации (отладка) |

Разделение на отдельные процессы `api` / `worker` возможно позже без изменения кода use cases — только другой composition root.

## 2. Ключевые решения

### ADR-1. Отслеживаем релиз-группы, а не релизы
Релиз в MusicBrainz — конкретное издание; у одного альбома их могут быть десятки (страны, форматы, ремастеры). Релиз-группа соответствует тому, что пользователь считает «новым альбомом». Дата — `first-release-date` релиз-группы.

### ADR-2. Каталог релизов общий, фильтры — на уровне пользователя
Релиз-группы исполнителя хранятся один раз (таблица `release_groups`), независимо от числа подписчиков. Фильтр по типам применяется при генерации уведомлений. Плюсы: один запрос к API на исполнителя, смена фильтра не требует перезагрузки.

### ADR-3. Baseline при подписке
Без baseline подписка на исполнителя с 30 альбомами дала бы 30 «новинок». При подписке текущие релиз-группы фиксируются в `subscription.baseline_at`; уведомляются только релиз-группы, обнаруженные позже, и уже найденные релизы с датой внутри окна `SYNC_STALE_DAYS` — чтобы в ленте сразу были свежие релизы нового исполнителя.

### ADR-4. Transactional outbox для уведомлений
Обнаружение релиза и создание записей в `notifications` происходит в одной транзакции. Отдельный воркер доставляет их (SMTP). Это даёт идемпотентность и повторы при сбоях SMTP. RSS читает из той же таблицы — канал «доставлен» в момент создания.

### ADR-5. Очередь задач в PostgreSQL
Фоновые задачи (импорт, синк исполнителя, отправка email) берутся через `SELECT … FOR UPDATE SKIP LOCKED`. Отдельный брокер (Redis/RabbitMQ) для данного масштаба не нужен.

### ADR-6. Глобальный rate limiter для MusicBrainz
Все обращения к MusicBrainz идут через один клиент с `golang.org/x/time/rate` (1 req/s, burst 1). Ограничение — на процесс; при горизонтальном масштабировании воркер синхронизации должен быть один (или лимитер переносится в Postgres advisory lock / Redis).

### ADR-7. Интерфейсы объявляются у потребителя
По Go-идиоме и DIP интерфейсы портов (`ArtistRepository`, `MusicCatalog`, `Notifier`, …) объявляются в слое use cases, а не в адаптерах.

### ADR-8. Однопользовательский режим
Приложение — личный инстанс. Нет таблицы пользователей, регистрации и аутентификации: глобальные настройки — singleton-таблица `settings`. Это убирает `user_id` из всех таблиц и use cases. Приложение рассчитано на доверенную сеть (localhost, домашняя сеть, VPN); если нужен доступ снаружи, защиту берёт на себя reverse proxy. RSS-фиды адресуются секретным токеном.

### ADR-9. Роль исполнителя в credit хранится в связке
Релиз-группы загружаются с `inc=artist-credits`; для каждой пары «исполнитель — релиз-группа» вычисляется роль `main` / `collaboration` / `featured` (см. [07-musicbrainz.md](07-musicbrainz.md#5-определение-роли-в-artist-credit)). Featuring-релизы сохраняются всегда, а флаг `include_featured` (глобальный и на подписку) применяется при fan-out.

### ADR-10. Синхронизация и дайджест — разные расписания
Синк ежедневный (свежая RSS-лента), email-дайджест — daily или weekly по настройке. Email-уведомления копятся в outbox со статусом `pending` до ближайшего `next_digest_at`.

## 3. Основные потоки

### 3.1 Подписка на исполнителя
1. SPA → `GET /api/v1/catalog/artists?q=radiohead` → use case `SearchArtists` → MusicBrainz.
2. Пользователь выбирает (и при желании включает featuring) → `POST /api/v1/subscriptions {mbid, include_featured}`.
3. `Subscribe`: upsert `artists`, создать `subscriptions`; если исполнитель новый в системе — поставить задачу `sync_artist(baseline=true)`.

### 3.2 Ежедневная синхронизация
1. Scheduler (cron) создаёт `sync_run` и задачи `sync_artist` для всех исполнителей, у которых есть хотя бы одна подписка.
2. Воркер для каждого исполнителя: загрузить все релиз-группы с artist credits → вычислить роль → diff с БД → новые вставить.
3. Для каждой новой релиз-группы: применить фильтры подписки (типы, featuring, анонсы) → создать `notifications` (email — `pending`, rss — сразу `sent`).

### 3.3 Email-дайджест
1. Планировщик раз в минуту проверяет `settings.next_digest_at`.
2. Когда время пришло — задача `send_digest`: все `pending` email-уведомления → одно письмо → `sent`; пересчитать `next_digest_at` (daily/weekly).

### 3.4 Импорт из файла
1. `POST /api/v1/imports` (multipart) → создать `import_job` + `import_items`, вернуть `202 Accepted`.
2. Воркер обрабатывает строки: MBID → lookup; имя → поиск + эвристика уверенности.
3. Неоднозначные → статус `needs_review` с кандидатами; пользователь выбирает через `POST /imports/{id}/items/{itemId}/resolve`.

Подробно — в [07-musicbrainz.md](07-musicbrainz.md) и [08-notifications.md](08-notifications.md).
